# 04 — Active Directory

> ✅ **STATUS: complete.** Walked end to end on 2026-10-02.

**Goal:** promote the Domain Controller to a new forest `lab.local`, join the
Windows Victim, seed users (including a Kerberoastable service account), and turn
on the Windows audit logging that makes attacks detectable.

## Passwords

The DSRM and `labadmin` passwords are generated by Terraform and stored in SSM
Parameter Store. The commands below read them directly on the DC, so you never
type them. To see one yourself, use the commands from `terraform output`
(`get_domain_admin_password_command`, `get_dsrm_password_command`). The other
lab users have fixed, published passwords (see step 2).

## Before you start: give hosts readable names

Out of the box, Fleet and Discover show hosts as `EC2AMAZ-XXXXXXX` (Windows) and
`ip-10-10-x-x` (Linux), so you can't tell them apart. Rename them **now, before
promoting the DC**. Renaming a domain controller after promotion is a much
bigger job.

To see which instance currently has which name:

```powershell
aws ssm describe-instance-information --region us-east-1 --query "InstanceInformationList[].[InstanceId,ComputerName]" --output text
```

Open an SSM session to each host (`aws ssm start-session --region us-east-1 --target <instance-id>`)
and run:

The names follow the common `<role><number>` convention: a short role code plus
a two-digit number. The domain supplies the "lab" part (`ws01.lab.local`).

| Host | New name | Command |
|---|---|---|
| Domain Controller | `DC01` | `Rename-Computer -NewName DC01 -Restart` |
| Windows Victim | `WS01` (workstation) | `Rename-Computer -NewName WS01 -Restart` |
| Linux Victim | `srv01` (server) | see below |
| Attack Server | `atk01` | see below (swap in `atk01`) |
| Elastic host | `siem01` | see below |

Windows names must be 15 characters or fewer. Each Windows host reboots and your
SSM session drops; reconnect after about 2 minutes. Windows shows names in
capitals (`WS01`); Elastic stores them lowercase, so KQL queries use
`host.name : "ws01"`.

On each Linux host, run all three:

```bash
sudo hostnamectl set-hostname srv01
echo 'preserve_hostname: true' | sudo tee /etc/cloud/cloud.cfg.d/99-keep-hostname.cfg
sudo systemctl restart elastic-agent
```

The middle line stops cloud-init from resetting the name on the next boot.

> Walked on the live lab 2026-10-10.

On the **Elastic host**, first comment out `cluster.initial_master_nodes`. Setup
wrote the old hostname there, and the setting is only needed the very first time
the cluster starts. Then rename and restart:

```bash
sudo sed -i 's/^cluster.initial_master_nodes/#cluster.initial_master_nodes/' /etc/elasticsearch/elasticsearch.yml
sudo hostnamectl set-hostname siem01
echo 'preserve_hostname: true' | sudo tee /etc/cloud/cloud.cfg.d/99-keep-hostname.cfg
sudo systemctl restart elasticsearch kibana elastic-agent
```

Agents and Fleet Server reach Elasticsearch by IP, not by hostname, so the
self-signed certificates keep working. Check with
`curl -k -u elastic https://localhost:9200/_cluster/health` (expect
`"status":"green"` or `"yellow"`).

**Check:** Fleet → Agents shows the new names on the same rows (no re-enrollment
needed). Events collected before the rename keep the old name.

### Renaming hosts in a lab that's already built

> Walked on the live lab 2026-10-10.

If the lab was built under the old names (`WIN-VICTIM`, `linux-victim`,
`attacker`, `ip-10-10-x-x`), the Linux commands above work as-is. Three things
are different:

- **WS01 is domain-joined**, so the rename needs a domain admin credential.
  Read it from SSM, as in the join step:

  ```powershell
  $cred = New-Object System.Management.Automation.PSCredential("LAB\labadmin", (ConvertTo-SecureString (Get-SSMParameterValue -Name "/detection-lab/domain_admin_password" -WithDecryption $true -Region us-east-1).Parameters[0].Value -AsPlainText -Force)); Rename-Computer -NewName WS01 -DomainCredential $cred -Restart
  ```

- **DC01 keeps its name.** Renaming a promoted domain controller isn't worth the
  risk.
- **Anything that filters on the old name stops matching.** Update the
  `Sysmon silent` health rule's query to `host.name : "ws01"` and rename it
  `Sysmon silent - ws01` (or re-import
  [`detections/health-sysmon-silent-ws01.ndjson`](../detections/health-sysmon-silent-ws01.ndjson)).
  Searches across the rename date need both names, e.g.
  `host.name : ("ws01" or "win-victim")`.

## Outline

### On the Domain Controller

```powershell
# 1. Promote to a new forest
Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
Import-Module ADDSDeployment
# DSRM password: read it straight from SSM Parameter Store so nothing is typed.
$dsrm = ConvertTo-SecureString (Get-SSMParameterValue -Name "/detection-lab/dsrm_password" -WithDecryption $true -Region us-east-1).Parameters[0].Value -AsPlainText -Force
Install-ADDSForest -DomainName "lab.local" -DomainNetbiosName "LAB" -SafeModeAdministratorPassword $dsrm -InstallDns -Force
# Takes several minutes, then reboots automatically. DNS delegation and
# cryptography warnings are expected.
```

> **Keep `Install-ADDSForest` on one line.** A backtick (`` ` ``) only continues
> a line if it's the very last character. Anything after it, even a comment,
> splits the command, and `-InstallDns -Force` runs on its own and fails.
>
> If you type the DSRM password at a `Read-Host` prompt instead, a mistyped or
> mangled paste fails with "does not meet the password complexity requirements".
> The generated password does meet them.
>
> **The promotion prints warnings. All are expected; ignore them.** Each appears
> twice (once in the pre-checks, once during the install):
>
> - *"…does not have static IP address(es)…"*. AWS hands out the IP by DHCP, but
>   it stays the same for the instance's lifetime. Don't set a static IP inside
>   Windows on EC2.
> - *"A delegation for this DNS server cannot be created…"*. Nobody owns `.local`,
>   so there's no parent zone to register with. Only lab machines need to find
>   `lab.local`, and they ask the DC directly.
> - *"Allow cryptography algorithms compatible with Windows NT 4.0"*. This is just a
>   notice that old weak crypto is off by default. Leave it off.
>
> Your SSM session drops when the DC reboots. That's the promotion finishing, not
> failing.

After reboot (wait ~5 minutes), open a new SSM session to the DC and seed
identities. Run each line on its own; none of them prompt for input.

| Account | Password | Why |
|---|---|---|
| `labadmin` | generated, `/detection-lab/domain_admin_password` | Your domain admin. Read from SSM so it's never typed. |
| `svc_sql` | `P@ssw0rd` | **Deliberately weak.** It's in the `rockyou.txt` wordlist, so the Kerberoasting attack can actually crack it. |
| `alice` | `Winter-Lab-2026!` | Ordinary user |
| `bob` | `Autumn-Lab-2026!` | Ordinary user |

> These passwords are published in this repo on purpose. They only exist inside
> the lab's private network. Never reuse them anywhere real.

**2. A domain admin**

```powershell
$da = ConvertTo-SecureString (Get-SSMParameterValue -Name "/detection-lab/domain_admin_password" -WithDecryption $true -Region us-east-1).Parameters[0].Value -AsPlainText -Force
```
```powershell
New-ADUser -Name "labadmin" -SamAccountName "labadmin" -UserPrincipalName "labadmin@lab.local" -AccountPassword $da -PasswordNeverExpires $true -Enabled $true
```
```powershell
Add-ADGroupMember -Identity "Domain Admins" -Members "labadmin"
```

**3. A Kerberoastable service account.** An account with a Service Principal
Name (SPN) can have a Kerberos ticket requested for it by *any* domain user, and
that ticket is encrypted with the account's password. That's what makes
Kerberoasting work.

```powershell
New-ADUser -Name "svc_sql" -SamAccountName "svc_sql" -UserPrincipalName "svc_sql@lab.local" -Description "SQL service account" -AccountPassword (ConvertTo-SecureString 'P@ssw0rd' -AsPlainText -Force) -PasswordNeverExpires $true -Enabled $true
```
```powershell
setspn -S MSSQLSvc/sql.lab.local:1433 svc_sql
```

**4. Two standard users**

```powershell
New-ADUser -Name "alice" -SamAccountName "alice" -UserPrincipalName "alice@lab.local" -AccountPassword (ConvertTo-SecureString 'Winter-Lab-2026!' -AsPlainText -Force) -PasswordNeverExpires $true -Enabled $true
```
```powershell
New-ADUser -Name "bob" -SamAccountName "bob" -UserPrincipalName "bob@lab.local" -AccountPassword (ConvertTo-SecureString 'Autumn-Lab-2026!' -AsPlainText -Force) -PasswordNeverExpires $true -Enabled $true
```

Use **single quotes** around the passwords. In double quotes, PowerShell treats
`$` and backticks as special characters and silently changes the password.

> **A password can't contain the username.** Windows' complexity rule rejects
> any password containing the account name (3+ characters, any case), so
> `Bob-Lab-2026!` fails for `bob` with "does not meet the length, complexity, or
> history requirement". When that happens, `New-ADUser` **still creates the
> account, disabled and with no password**. Rerunning `New-ADUser` then fails
> with "already exists". Fix the existing account instead:
>
> ```powershell
> Set-ADAccountPassword -Identity bob -Reset -NewPassword (ConvertTo-SecureString 'Autumn-Lab-2026!' -AsPlainText -Force)
> ```
> ```powershell
> Enable-ADAccount -Identity bob
> ```

**Check:**

```powershell
Get-ADUser -Filter 'Name -like "labadmin" -or Name -like "svc_sql" -or Name -like "alice" -or Name -like "bob"' -Properties ServicePrincipalName,MemberOf | Select-Object Name,Enabled,ServicePrincipalName
```

You should see four enabled users, with `MSSQLSvc/sql.lab.local:1433` on
`svc_sql`. In Kibana, each account creation shows up as event `4720` on DC01.

### Audit policy (the highest-value logging you can enable)

Windows logs very little detail by default. This section turns on the events
the walkthroughs rely on. It has two halves:

- **A Group Policy Object (GPO)** for two registry settings. Linked to the whole
  domain, it applies automatically to DC01 now and to WS01 once it joins.
- **`auditpol`** for the audit categories, run on each Windows host. (Setting
  these through a GPO means hand-editing files in SYSVOL, which isn't worth it
  for a lab.)

| Setting | Event ID | What you get |
|---|---|---|
| Include command line in process creation | 4688 | Full command line of every new process (Windows' own version of Sysmon event 1) |
| PowerShell script block logging | 4104 | The actual PowerShell code that ran, even if obfuscated or encoded. Key for T1059.001. |
| Process Creation | 4688 | A new process started |
| Logon / Special Logon | 4624, 4625, 4672 | Successful and failed logons, admin logons |
| Credential Validation | 4776 | NTLM password checks |
| Kerberos Authentication Service | 4768, 4771 | Kerberos logon tickets (DC only) |
| Kerberos Service Ticket Operations | 4769 | Service tickets. This is what Kerberoasting produces (DC only). |
| User Account / Security Group Management | 4720, 4728, 4732… | Accounts created, added to groups |

**On DC01**, create the GPO and link it to the domain:

```powershell
New-GPO -Name "Lab Audit Logging" | New-GPLink -Target "DC=lab,DC=local"
```
```powershell
Set-GPRegistryValue -Name "Lab Audit Logging" -Key "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System\Audit" -ValueName ProcessCreationIncludeCmdLine_Enabled -Type DWord -Value 1
```
```powershell
Set-GPRegistryValue -Name "Lab Audit Logging" -Key "HKLM\Software\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -ValueName EnableScriptBlockLogging -Type DWord -Value 1
```
```powershell
gpupdate /force
```

**On DC01** (and later on WS01, after it joins), enable the audit categories:

```powershell
"Process Creation","Logon","Special Logon","Credential Validation","Kerberos Authentication Service","Kerberos Service Ticket Operations","User Account Management","Security Group Management" | ForEach-Object { auditpol /set /subcategory:"$_" /success:enable /failure:enable }
```

Each category should print `The command was successfully executed.`

**Check:**

```powershell
auditpol /get /category:"Detailed Tracking","Logon/Logoff","Account Logon","Account Management"
```
```powershell
Get-ItemProperty "HKLM:\Software\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging"
```

The eight categories show `Success and Failure`, and the second command shows
`EnableScriptBlockLogging : 1`.

**See it in Kibana:** run any PowerShell command on DC01 (e.g. `Get-Service | Select-Object -First 1`),
wait a minute, then search Discover:

```
host.name : "dc01" and event.code : ("4688" or "4104")
```

4688 events carry the full command line in `process.command_line`; 4104 events
carry the script text in `powershell.file.script_block_text`.

### Join the Windows Victim

All commands run in an SSM session **on WS01**.

**1. Make sure WS01 can find the domain.** It must use DC01 for DNS:

```powershell
Resolve-DnsName lab.local
```

If that fails, point DNS at DC01's private IP (`ipconfig` on DC01 shows it):

```powershell
Set-DnsClientServerAddress -InterfaceIndex (Get-NetAdapter | Where-Object Status -eq Up).ifIndex -ServerAddresses <DC-private-IP>
```

**2. Join, reading `labadmin`'s password from SSM.** Don't use
`-Credential (Get-Credential)`. In an SSM session there's no pop-up, so it stops
at a bare `Credential` text prompt that's easy to cancel without noticing, and
then nothing gets joined.

```powershell
$cred = New-Object System.Management.Automation.PSCredential("LAB\labadmin", (ConvertTo-SecureString (Get-SSMParameterValue -Name "/detection-lab/domain_admin_password" -WithDecryption $true -Region us-east-1).Parameters[0].Value -AsPlainText -Force)); Add-Computer -DomainName "lab.local" -Credential $cred -Verbose
```

This deliberately leaves off `-Restart`, so any error stays on screen. Success is
a yellow `WARNING: The changes will take effect after you restart the computer`.
Then:

```powershell
Restart-Computer -Force
```

**Check** (reconnect after ~2 minutes):

```powershell
(Get-CimInstance Win32_ComputerSystem) | Select-Object Name, Domain, PartOfDomain
```

Expect `Domain : lab.local` and `PartOfDomain : True`. On DC01,
`Get-ADComputer WS01` should return the computer account.

> **Join "didn't happen" with no error?** Check `C:\Windows\debug\NetSetup.LOG` on
> WS01. If its newest entries predate today, `Add-Computer` never reached
> the DC (e.g. the credential prompt was cancelled). Rerun step 2.

## Verify

`4688` process-creation events with command lines, and `4624/4625` logons, appear
in Kibana. A Kerberoast attempt against `svc_sql` later produces `4769`.
